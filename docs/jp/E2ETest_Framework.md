# 4 層アーキテクチャの設計思想

E2E テストが数十本を超えたあたりで、多くのチームが同じ壁に当たる。UI が少し変わるたびに何十ファイルも直す。誰かが書いた便利メソッドが別のテストを壊す。緑のまま何も検証していないテストが増える。本書は、その壁の正体を「責務の混在」と捉え、E2E テストを 4 つの層に分離する設計の**なぜ**を説明する。

本書は思想を語る文書であり、具体的な実装・手順・規約は扱わない（それらの正本は [`for-claude-code/`](../../for-claude-code/README.md) の rules / skills / gate にあり、実装とともに更新され続ける）。本書が語る内容は、実装がどう変わっても真であり続けることを意図している。

---

## 1. なぜ層を分けるのか — 変更理由の分離

E2E テストのコードが変更を迫られる理由は、実は 4 種類しかない。

| 変更の発生源 | 例 |
|---|---|
| **UI 構造が変わった** | ボタンの DOM 位置・セレクタ・画面レイアウトの変更 |
| **業務手順が変わった** | 「登録 → 承認」だったフローに確認ステップが挟まった |
| **テスト観点が変わった** | 検証すべき期待結果の追加・変更 |
| **環境が変わった** | URL・認証情報・タイムアウトの妥当値 |

1 つのテストファイルにセレクタと操作手順と期待値と環境値が同居していると、この 4 種類の変更がすべて同じファイルに着地する。逆に、変更理由ごとに層を分ければ、**どの種類の変更が来ても、直す場所は 1 つの層に閉じる**。

```
Layer 4: Config/Env     ← 環境の変更だけがここに着地する
Layer 3: Tests          ← テスト観点の変更だけがここに着地する
   ↕ Fixture            ← 層ではなく、層をつなぐ配線（§3 参照）
Layer 2: Actions        ← 業務手順の変更だけがここに着地する
Layer 1: Page Objects   ← UI 構造の変更だけがここに着地する
```

これは単一責任の原則（「変更理由が 1 つであること」）を E2E テストに適用した形にすぎない。UI が変わったとき Page Object だけを直せばテストが全部生き返る、という体験がこの構造の価値のすべてである。

## 2. 各層の責務 — 何であって、何でないか

### Layer 1: Page Objects — UI の「意味の辞書」

Page Object は「この画面のこの要素は、こういう意味を持つ」を定義する辞書である。ログインボタン・検索入力欄・結果テーブルといった**意味**に名前を与え、その意味が DOM 上のどこにあるか（Locator）を一元管理する。

Page Object が持ってよいのは、要素の定義・単一要素への基本操作・状態の観測まで。**ビジネスの文脈を知ってはならない**。「検索ボタンを押す」は書けるが、「商品を探して購入する」を知っているのは上の層の仕事である。辞書が物語を語り始めると、UI 変更のたびに物語ごと壊れる。

Locator の設計自体にも独立した思想体系がある（[Locator Strategy](./LOCATOR/locator_strategy.md) 参照）。要点だけ言えば: Locator は「未来に成立する条件式」であり、構造ではなく意味で書き、探索空間を局所化する。

### Layer 2: Actions — ユーザーストーリーの「動詞」

Action は「ログインする」「商品を検索する」「申請を承認する」といった、ユーザーストーリーに現れる動詞を実装する。複数の Page Object をまたぎ、複数画面を制御し、業務として意味のある単位のフローを 1 メソッドで提供する。

Action の価値は**再利用**にある。「ログインする」はほぼすべてのテストの前提であり、その実装が 1 箇所にあれば、ログイン画面の手順変更はその 1 箇所の修正で済む。だからこそ Action はテスト固有の事情（このテストではこの値を期待する、など）を持ち込んではならない。**アサーションはテストの関心事であり、Action に書いた瞬間、その Action は特定のテスト専用になって再利用性を失う**。

### Layer 3: Tests — 期待の「宣言」

テストは「何をしたら、何が起きるべきか」の宣言である。理想のテストコードは、Action の動詞を並べた手順と、期待結果の検証だけでできている — つまり**自然言語のテスト手順書とほぼ 1:1 に対応する**。

テストが Locator や DOM 構造を知る必要はない。知ってしまうと、UI 変更がテスト観点の変更でもないのにテストファイルを書き換えさせる — 層分離が守ろうとした利益がそこで消える。

### Layer 4: Config/Env — 環境の「吸収材」

URL・認証情報・タイムアウト・共通セレクタといった「環境や運用判断で変わる値」を一元管理する。値がコードに散らばっていると、環境の変更が全層への横断修正になる。認証情報を環境変数に隔離するのはセキュリティの要請でもある。

## 3. 境界はなぜ「絶対」なのか

層の定義だけなら誰でも守れる。難しいのは境界の維持である。「今回だけテストに Locator を直書き」「この Action にだけ expect」— 一つひとつは合理的に見える例外が、数ヶ月で層構造を溶かす。だからこの設計では境界を**絶対境界**として扱い、例外を認めない。

とりわけ重要な境界が 2 つある。

**テストに Locator を書かない / Action に expect を書かない。** この 2 つを同時に守ると「Action はどうやって検証結果を返すのか」という問題が生じる。答えは、Action が**状態を観測して boolean を返し**（verify メソッド）、テストがその戻り値を expect で検証する、という役割分担である。検証の「観測」と「判定」を層で分けることで、観測ロジックは再利用可能なまま、判定はテストの宣言として残る。

**依存は注入する。** テストが Action を手動で組み立てる（new する）と、テストと Action の結合が暗黙化し、共有すべきインフラ（ステップ記録・カウンタ等）の配線が各テストに漏れ出す。依存注入（Fixture）を通すことで、テストは「どの動詞を使うか」を宣言するだけになり、配線は 1 箇所に集約される。

ここで、冒頭の図（§1）が Fixture を第 5 の層として描いていない理由を明確にしておく。層は「変更理由」で切られているが、**Fixture には固有の変更理由がない** — UI 構造も業務手順もテスト観点も環境値も持たず、変わるのは新しい動詞（Action）が登録されるときだけである。つまり Fixture は層ではなく**層と層をつなぐ配線**であり、同時に絶対境界の**強制装置**でもある。テストが検証手段（test / expect）も動詞（Action）も Fixture 経由で受け取るよう配線しておけば、正しい書き方が最も楽な書き方になり、境界侵食（テストが Action を手で組み立てる・テストランナーを直接 import して野良の検証経路を作る）は**配線を迂回する明示的な逸脱**としてしか書けなくなる — そして明示的な逸脱は機械的に検出できる（§4）。境界が数ヶ月後も生きているのは守る人の意志が強いからではなく、守る側に構造の重力が働き、破る側が検出可能な形でしか存在できないからである。

## 4. 偽陽性との戦い — この設計が本当に守っているもの

E2E テストの最大の敵は、落ちるテストではない。**通ってはいけないのに通るテスト**である。緑のまま検証だけが死んでいるテストは、存在しない安心を配り続け、発見が遅れるほど高くつく。

4 層の境界も、その上に載る規範（固定待機を検証メソッドに置かない・エラーを握りつぶして false を返さない・テスト条件を満たせないときに黙ってスキップしない）も、突き詰めればすべて同じ一つの原則から導かれている:

> **テストは失敗できることに価値がある。失敗する能力を静かに失う経路を、構造で塞ぐ。**

「動く」と「正しい」は別物である。特に生成 AI がテストコードを書く時代には、「動くが検証していない」コードが人間の想像より速く増殖する — AI は既存コードを正解パターンとして模倣するため、偽陽性パターンが 1 つ混入すると複製され続ける。だからこの設計では、規範を散文で言い聞かせることに頼らず、**機械的に検出できる違反は機械が検出する**（運用セットの gate がその実装である）。

## 5. 規範はどこに置くべきか — 本書の位置づけ

最後に、この文書自身の設計判断を記しておく。規範には 2 種類ある。

- **実装が変わっても真であり続ける思想** — なぜ層を分けるのか、なぜ境界は絶対か、なぜ偽陽性と戦うのか。本書と [Locator Strategy](./LOCATOR/locator_strategy.md) が担う
- **実装とともに変わり続ける運用規範** — 具体的な禁止パターン・雛形・手順・しきい値。これらは強制力のある場所（AI が常時ロードする rules・フェーズごとに読む skills・exit code で判定する gate）に置かなければ機能しない。ドキュメントは読まれなくても実装が進んでしまうからである

運用規範の正本は [`for-claude-code/`](../../for-claude-code/README.md) にある。本書に手順や規約が書かれていないのは、書き忘れではなく、**ドリフトしない文書には実装を書かない**という選択の結果である。
